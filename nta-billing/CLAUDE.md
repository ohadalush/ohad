# נת"ע — הפקת כתבי כמויות (חלונות אלומיניום / מיגון)

אתה עובד עבור אוהד. בכל הזמנה הקלט הוא קובץ "סיכום" מ-QuantCalc. הפלט: כתב כמויות ב-Excel, PDF פירוט כמויות, חשבון מאוחד, רשימת הזמנות ו"פורמט נתע".
**כל החישוב נעשה בקוד (`cli.py` + `engine/`).** התפקיד שלך הוא להריץ את הפקודות, לקרוא את הפלט הקצר שלהן, לשאול כשצריך ולדווח. אל תחשב בראש, ואל תפתח קבצי Excel גדולים כשיש פקודה שעונה על השאלה.

תשובות קצרות בעברית. תמיד מציינים את הנתיב לקובץ שנוצר. כשהמשתמש שואל "כמה זה הוסיף", עונים אחרי הנחות (‎×0.85×1.05, לפני מע"מ).

## פקודות (מהתיקייה הראשית)

```
python cli.py inspect <קובץ>                         # קריאה + overrides מוצעים + שאלות פתוחות. לא בונה כלום
python cli.py add <קובץ> --account N [--set CODE=VAL ...] [--force]
python cli.py query <קובץ> [--set ...]                # שאילתא: בונה קבצים ל-output/שאילתות, לא שומר לחשבון
python cli.py set N <הזמנה> CODE=VAL [CODE=auto]      # שינוי override + בנייה מחדש + "שינוי אחרי הנחות"
python cli.py meta N <הזמנה> --address .. --floor .. --apt .. [--name ..]
python cli.py lines N <הזמנה>                         # השורות הלא-אפסיות של הזמנה + ה-overrides שלה
python cli.py list N                                  # טבלת הזמנות + סכומים
python cli.py remove N <הזמנה>
python cli.py build N                                 # חשבון מאוחד + רשימת הזמנות + פורמט נתע + 4 בדיקות ביקורת
```

- **קבצים נכנסים:** `inbox/`.
- **תוצרים:** `output/חשבון N/`.
- **מצב החשבון:** `accounts/חשבון_N_נתונים.json`.
- **החשבון הפתוח כרגע: 7.**
- **ערך override:** מספר, או נוסחה עם `{D:קוד}` `{E:קוד}` `{I:קוד}` `{L:שם שדה}`. **לעולם לא לכתוב מספרי שורות** (למשל `D88`), כי הם נשברים כשהתבנית גדלה.

## תהליך הוספת הזמנה

1. מריצים `add`. הפקודה קוראת את **שני** הגיליונות (סיכומים ופירוט אלמנטים), משייכת כל אלמנט לסוגר לפי שטח היחידה ומספר המסלולים, מוסיפה ידיות לפי כתובת ואת קיזוז זכוכית ארגז התריס, ומזהה הזמנות "ארגזי תריס בלבד".
2. **אם יצא קוד 2 עם "⚠ לשאול"**, עוצרים ושואלים את המשתמש. לא מנחשים: לא קוד סעיף, לא מחיר ולא פיצול. אחרי התשובה מריצים שוב עם `--set ...` ו-`--force`.
3. **בדיקת שפיות:** לוודא שסוג התריס (רגיל או אור) תואם את הפירוט. **אסור** תריסי אור ותריסים רגילים יחד באותו אלמנט.
4. **מדווחים:** סה"כ, כולל מע"מ, ונתיבי הקבצים. שולחים לאוהד את ה-Excel ואת ה-PDF של פירוט הכמויות.
5. **לא מריצים `build` אחרי הזמנה.** חשבון מאוחד ופורמט נתע נבנים רק כשאוהד אומר שסיימנו את החשבון ("תייצא את חשבון N").

**סעיף חדש שלא קיים במחירון:**
- מוסיפים אותו ל-`engine/order_template.py` עם תיאור **מילה במילה** מהמחירון.
- **באותו שינוי** מוסיפים לו כלל ב-`engine/rules.py` (לפחות `("const", 0)`). בלי כלל, התא נשאר ריק ומחזיר `#VALUE!` בחשבון המאוחד.
- קידומת פרק חדשה מוסיפים ל-`CHAPTERS` ב-`engine/generate.py`.
- **אחרי שינוי בתבנית מריצים `build` לחשבון הפתוח** כדי לוודא שהכול תקין.

## כללים שנלמדו (לא לשבור)

**override ברמת הזמנה תמיד:** כל תיקון חד-פעמי הוא override להזמנה. לא משנים את `rules.py` או את `suggest.py`, אלא אם אוהד מבקש שינוי גלובלי במפורש.

**סוגריים:**
- הסוגר נקבע לפי שטח **יחידה** ולא לפי הסכום.
- שטח מתחת לטווח נכנס לסוגר התחתון, ושטח מעל הטווח נכנס לסוגר העליון. **תמיד בשטח האמיתי, בלי חיתוך** (אושר).
- הטבלאות המלאות: `docs/RULEBOOK.md`.

**תוספת 15% לחלק קבוע (12.011.1001):** Σ(שטח הזזה+קבוע × מחיר הסוגר שבו האלמנט נמצא בפועל).

**קיפ+קבוע, דרייקיפ+קבוע, חלון ציר, 12.011.0280 (זכוכית 6+10+10), כתובת לא מוכרת:** תמיד שואלים.

**זכוכית:**
- היעד הוא 6+10+8 (12.068.1216). כל זכוכית אחרת מקבלת קיזוז דרך הדליים 1172 / 1004 / 1006, והסכום עובר ליעד.
- ממנו מחסירים את `קיזוז זכוכית לארגז תריס` (שדה QuantCalc שמגיע מתוספת 30 ס"מ ארגז). `suggest` עושה זאת אוטומטית.
- הזמנת חריגה (יעד 5+0.76+5, קוד 12.068.1320) רק אם אוהד אומר זאת במפורש.

**כתובות:**

| כתובת | סוג תריס | ידיות סיבוביות |
|---|---|---|
| משה רינת 2, מנחם בגין 48 | רגיל | **כן** |
| שולמית אלוני 15, משה רינת 4 ו-10, מנחם בגין 40/50/52 | אור | לא |

- ידיות: 12.99.0002 = מספר אלמנטי החלון, 12.99.0001 = מספר הוויטרינות.
- אם הפירוט סותר את הכתובת, הולכים לפי הפירוט ומציינים זאת.

**אין תריס בהזמנה:** כל סעיפי פירוק התריס והארגז הם 0.

**רשת יתושים:** תוספת ידנית = override ל-12.067.0210 בלבד. את הפירוק (12.067.9000) לא משנים, אלא אם נאמר אחרת.

**מחירים:** 60.020.0067 (צוות אלומיניום) = **3,400** (אושר, למרות שבמחירון נתע 3,500).

**צוותים מיוחדים** (override בלבד):

| סעיף | מחיר |
|---|---|
| 60.020.0105 חשמל | 3,500 |
| 60.010.0110 בנייה/גבס | 3,550 |
| 60.010.0120 ריצוף | 3,650 |

**כוח אדם ומנוף:**
- 60.010.0020 פועל פשוט = 3.
- 60.010.0010 פועל מקצועי = מנוע 90–120+ ×2 + שאר המנועים + `כמות טיפול בארגז`.
- מנוף לפי קומה: 2 אם סכום המנועים ≥5, אחרת 1.

**ארגזי תריס בלבד:** `60.020.0067=1` ו-`60.010.0020=0`. הפועל המקצועי מחושב כרגיל. `suggest` מזהה את סוג ההזמנה הזה לבד.

**ייבוא חשבון חיצוני מחושב מראש ("השלמה", מספר 9999 או 0000):**
- כל כמות הופכת ל-override (מבנה הקובץ יכול להיות שונה, למשל כמות בעמודה H).
- **מאפסים במפורש** כל סעיף שאצלנו מחושב אוטומטית ובמקור הוא 0.
- לא מוסיפים שום דבר שלא קיים במקור.
- בודקים שהסה"כ זהה לסה"כ של המשתמש.
- הזמנת ההשלמה תמיד אחרונה בחשבון (`build` ממיין זאת לבד).

**חשבון מאוחד:**
- סדר הגיליונות: ריכוז, רשימת כתובות, הזמנות.
- מוסתרות שורות 0 בגיליונות ההזמנה, ובריכוז רק לפי `סה"כ כמות חשבון`=0.

**פורמט נתע** (נוצר ב-`build`):
- סעיף שקיים בגיליון "12 - אלומיניום" נכנס לבלוק "חשבון N", בעמודת **כמות מדווחת מאוכלס**.
- כל סעיף אחר נכנס ל"סעיפים חסרים" (עמודה R, והכותרת P1 משתנה ל"חשבון N").
- רק חשבון אחד לכל קובץ. גיליונות החשמל והמיזוג לא נוגעים בהם.
- המחירים שלנו גוברים: מחירי נתע של סעיפים שבשימוש מסונכרנים למחירים שלנו.
- **הסכום חייב להיות זהה 1:1.** `build` בודק זאת ונכשל אם לא.

**ביקורת:** `build` מריץ את 4 הבדיקות. כשמשהו לא תואם, מוצאים את המקור תא-מול-תא, ולא מסתפקים ב"פער קטן".
